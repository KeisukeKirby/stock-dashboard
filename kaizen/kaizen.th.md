# บัญชี
> แนวคิด: ลดการคีย์และการกระทบยอด (ประสิทธิภาพ) เพื่อให้มีเวลาตรวจสอบทุกวัน (คุณภาพ)

### สรุป
- คาดว่าลดได้ **59.4 ชั่วโมงต่อเดือน (รวม 2 คน)** (NEE 31.4h / NUT 28.0h)
- ปัจจุบัน 2 คนใช้เวลา 193.6h ต่อเดือน (NEE 104.8h / NUT 88.8h)
- 31% ของ 193.6 ชั่วโมงต่อเดือน (2 คน) เวลาที่ได้คืนประมาณ 52.5 ชั่วโมงต่อเดือน ใช้กับการตรวจรายวัน บัญชีรายเดือน นับสต็อก และรายงานประจำเดือน

:::info วิธีคิดตัวเลข
ชั่วโมงทำงาน: จาก Daily Report ของ NUT และ NEE (11 ก.พ. – 3 เม.ย.) ไม่รวมงานปิดงบ / ที่คาดว่าลดได้: ประมาณการจากการวิเคราะห์ Daily Report ด้วย AI / 1 เดือน = 21 วันทำการ (จำนวนวันทำการเดือนนี้)
:::

- เวลาที่ได้คืนใช้กับ: ตรวจทุกวัน · คืนเงินได้รวดเร็ว · ส่งรายงานตรงเวลา
- เป้าหมาย: ป้องกันปัญหา
:::

## กระทบยอดขายทุกวัน และบันทึกคืนเงิน
:::proposal
ปัญหา: ตรวจแค่ทุกวันจันทร์ เจอส่วนต่างช้า และ E-Tax รอได้ถึงประมาณ 1 สัปดาห์

:::

### ① ธนาคาร: นำเข้ารายการ แล้วกระทบยอดด้วย AI
:::kv
ชั่วโมง (2 คน ต่อเดือน): 22.4h → 9.8h (−12.6h, −56%)
กลุ่ม: คุณภาพ · คีย์ข้อมูล
ย้ายไป AI: ต่ำ (คีย์เงินเข้า · แก้ใน PEAK = ต่ำ, กระทบยอดธนาคาร = ต่ำ)
:::

**วิธีที่ทำอยู่ตอนนี้**

- ดูรายการเดินบัญชีแล้วคีย์ยอดเงินเข้าเอง
- คีย์เงินเข้าจากร้านแยกอีกรอบ
- กระทบยอด 2–3 เดือนรวมกันใน Excel
- แก้ยอดที่ไม่ตรงใน PEAK

**ขั้นตอนใหม่**

1. **เช้าวันจันทร์**: ดาวน์โหลดรายการสัปดาห์ก่อนทุกบัญชี (KBank เป็น PDF, BBL เป็น CSV)
2. **ต่อจากนั้น**: นำเข้าไฟล์ธนาคารใน PEAK เลือกกระทบยอดด้วย AI
3. **ต่อจากนั้น**: ดูคู่ที่ AI เสนอ แล้วยืนยันรายการที่ถูกทั้งหมด
4. **ต่อจากนั้น**: หาสาเหตุเฉพาะรายการที่ไม่ตรง (เงินเข้าจากร้านเทียบกับยอด POS)
5. **สิ้นเดือน**: ตรวจยอดคงเหลือกับรายการเดินบัญชีในรายงาน (คนทำกับคนตรวจเป็นคนละคน)

:::tip
ไม่ต้องรวม 2–3 เดือนอีก งานกระทบยอดตอนปิดงบก็ลดลง
:::

### ③ Shopee · Lazada: ตรวจด้วยแมโคร PEAK ออกเลข
:::kv
ชั่วโมง (2 คน ต่อเดือน): 18.8h → 7.9h (−10.9h, −58%)
กลุ่ม: ประสิทธิภาพ · คีย์ข้อมูล
ย้ายไป AI: ต่ำ–กลาง (กระทบยอด Shopee · Lazada = ต่ำ, ออกเลข = กลาง, รายงาน VAT ขาย = กลาง)
:::

**วิธีที่ทำอยู่ตอนนี้**

- เทียบยอดขาย ค่าธรรมเนียม และเงินเข้าใน Excel
- เทียบเงินเข้ากับรายการเดินบัญชี
- แก้เลข 215–258 รายการทีละรายการทุกเดือน
- ยกเลิกรายการซ้ำเอง

**ขั้นตอนใหม่**

1. **ประมาณวันที่ 15**: ส่งออกข้อมูลออเดอร์ เงินเข้า และรายการธนาคาร
2. **ต่อจากนั้น**: บันทึกในโฟลเดอร์ของเดือน แล้วรันแมโคร
3. **แมโคร**: แยกเป็น ตรงกัน ยอดต่าง ยังไม่ได้รับเงิน และซ้ำ
4. **ต่อจากนั้น**: ตรวจเฉพาะส่วนต่างและยังไม่ได้รับเงิน เขียนสาเหตุ
5. **ต่อจากนั้น**: ส่งเข้า PEAK ให้ PEAK ออกเลข (ไม่แก้เลขใน Zort)
6. **ก่อน ภ.พ.30**: ตรวจยอดรวมในรายงาน VAT ขายของ PEAK TAX

:::tip
ต้องตรวจสอบ: PEAK ออกเลขเรียงตามวันที่ได้หรือไม่
:::

ปัญหา: ไม่รู้ว่าใครอยู่ที่ไหน
ใหม่: ทำตาราง “วันที่ × สาขา / อีเวนต์”
ตรวจ: ไม่มีช่องว่าง (ยังไม่มีคนประจำ)
:::

## ตารางกะ: ใครอยู่ไหน และเวลาเข้า-ออก
:::proposal
ใหม่: เจ้าหน้าที่ HR กรอกคนและเวลาเข้า-ออกของทุกสาขาและอีเวนต์ใน Store Staff Shift Schedule
:::

**เมื่อไร**: ตั้งแต่ 9 พ.ย.

### ขั้นตอน
1. กรอกคนและเวลา
2. ดูจำนวนวันประจำและวันลงเวลา ต่อ PC
3. ดูยอดขายคู่กับเวลาเข้า-ออก
4. ยอดเป็นศูนย์หรือเวลาผิดปกติ ไปดูหน้างาน

## ยอดตก ให้ไปดูหน้างาน
:::proposal
ปัญหา: ฟังแค่รายงานของ PC ไม่ไปดูหน้างาน ไม่วิเคราะห์สาเหตุ
ใหม่: ส่งคนที่ขายเก่งไปดูการขายที่หน้างาน
:::

- วิเคราะห์ทำเล กลุ่มลูกค้า และการทำงานของ PC แล้วใช้ในอีเวนต์ถัดไป
- HR ดูยอดขายต่อหลังจัดคน บัญชีเจอตัวเลขผิดปกติให้แจ้ง HR
- กะที่เป็นคนในครอบครัวคู่กัน ให้ตรวจหน้างานละเอียดกว่าปกติ

## แจ้งกิจกรรมล่วงหน้า
:::proposal
ปัญหา: แจ้งทำบุญแค่วันก่อน บางคนเตรียมไม่ทัน
ใหม่: แจ้งล่วงหน้าเรื่องประชุมและกำหนดการหรือกิจกรรมที่ต้องเตรียมตัว
:::

- ใส่ Google Calendar ก่อน

# อีคอมเมิร์ซและบริการลูกค้า
> รับเคลมเมื่อหลักฐานครบ

## เคลม: ต้องมีหลักฐานครบก่อน
:::proposal
ปัญหา: ไม่ได้ขอข้อมูลที่จำเป็น และข้ามขั้นตอน
ใหม่: ยังไม่ดำเนินการจนกว่าจะได้หลักฐานการซื้อและรูปความเสียหาย
ตรวจ: ไม่แน่ใจ ถามคุณชิมาดะหรือคุณ Bew
:::

### ขั้นตอน
1. ถ้าใช้เวลา ตอบว่า “ขอตรวจสอบก่อน”
2. หลักฐานการซื้อ + รูป จากลูกค้า
3. ซื้อจากร้านตัวแทน → แนะนำไปร้านนั้น
4. ซื้อจากเรา → ซ่อม เปลี่ยนรุ่นใหม่ หรือคืนเงิน

## ข้อความถึงลูกค้าต่างชาติ
:::proposal
ปัญหา: ส่งข้อความ AI ตรง ๆ และขอโทษหลายครั้งตั้งแต่ยังไม่รับเรื่อง
ใหม่: ก่อนตรวจข้อเท็จจริง พูดแค่ “Sorry to hear that”
:::

- สั่ง AI ว่า “สั้นและกระชับ”
- อ่านข้อความ AI ก่อนส่ง
- ไม่แน่ใจ ถาม AI หรือหัวหน้า

## ไม่ให้การยืนยันรับสินค้าล่าช้า [อยู่ระหว่างตรวจสอบ]
:::proposal
ปัญหา: ลูกค้าบางคนไม่กดยืนยันรับ ใช้เวลาถึง 30 วัน
ใหม่: หลังของถึง 3–4 วัน ดูลูกค้าที่ยังไม่ยืนยัน แล้วให้แอดมินขอให้กด
:::

# ทั้งบริษัท
> กฎที่ทุกคนต้องทำ และขั้นตอนเริ่มใช้

## เวรทิ้งขยะและทำความสะอาด
:::proposal
ปัญหา: โต๊ะรก ไม่มีคนรับผิดชอบห้องเตรียมเครื่องดื่มและขยะ
ใหม่: เวรตาม Trash & Cleaning Duty ทำในวันของตัวเอง โต๊ะทำเอง
ตรวจ: ช่องเช็กในตารางเวรครบทุกสัปดาห์
:::

**เมื่อไร**: หมุนเวียนรายสัปดาห์

**พื้นที่เวร**: ทิ้งขยะ · ห้องเตรียมเครื่องดื่ม · พื้นส่วนกลาง

## กฎพื้นฐานทุกวัน
:::proposal
ใหม่: ทุกคนทำตามขั้นตอนที่ตกลงกันเหมือนกัน
:::

- รายงานประจำวัน: งาน เวลา ปัญหา ทุกวัน
- ใช้ To Do List จัดตารางงานของตัวเอง
- เอกสารที่ให้ประธานหรือคุณ Bew เซ็น ผู้ทำเซ็นก่อน ผิดให้แก้เอง
- ข้อมูลจากร้านหรือคู่ค้า แจ้งกลุ่มภายในวันนั้น

## คำสั่งไม่มีกำหนดส่ง ทำให้เสร็จวันนั้น
:::proposal
ใหม่: วันที่ได้รับคำสั่งคือวันกำหนดส่ง
:::

- ทำให้เสร็จภายในวันนั้น
- ทำไม่ทัน ให้อธิบายคุณชิมาดะ และแจ้งว่าใช้เวลากี่วัน

## งานค้าง ต้องผลักดันเอง
:::proposal
ปัญหา: ไฟล์ป้ายค้างรออนุมัติ หลังคนทำลาออกก็ไม่มีใครตาม
ใหม่: ไฟล์เสร็จให้ขอใบเสนอราคาทันที ถ้าอนุมัติช้า ผู้รับผิดชอบตามคุณ Bew หรือประธาน
:::

## ขั้นตอน: ทบทวนใน 2 เดือน
:::proposal
ใหม่: เริ่มทำตามขั้นตอนใหม่ตั้งแต่วันเริ่ม
:::

:::flow
- ตั้งแต่วันเริ่ม: เริ่ม (ทำตามขั้นตอนใหม่)
- ทุกวันศุกร์: ติดตามผล (15 นาที: ความคืบหน้าและปัญหา)
- หลัง 1 เดือน: ตรวจกลางทาง (ปรับขั้นตอนเล็กน้อย)
- หลัง 2 เดือน: ทบทวน (ตัดสินใจหยุดหรือแก้)
:::

- รายงานประจำวันทุกวัน ออฟฟิศใช้ AI วิเคราะห์เพื่อติดตามผล
- กรณีพิเศษหรือปัญหา ไม่ต้องหยุดงาน แจ้งกลุ่มภายในวันนั้น
- ประชุมประจำเดือน ตัดสินว่าทำต่อ แก้ หรือหยุด

| 15 | รายงานผล | ผู้ประสานงาน → ชิมาดะ |

### หลังปิดงาน: Case ① หรือ ②
| Case | เมื่อไร | ขั้นต่อไป |
|---|---|---|
| Case ① | ปกติ | ⑬ โอนกลับคลังหลัก (Zort) → ⑭ เก็บขึ้นชั้น → ⑮ รายงานผล |
| Case ② | อีเวนต์ถัดไปภายใน 2 สัปดาห์ ขนาดเท่าเดิมขึ้นไป | ซีลแล้วเก็บที่พื้นที่พักสินค้า (ข้าม ⑬⑭) → ⑮ รายงานผล ระหว่างรอห้ามขายที่ร้านหรือออนไลน์ |

### ตรวจที่ไหน ใคร อะไร
| ขั้นตอน | ใคร | ตรวจอะไร | ทำอย่างไร |
|---|---|---|---|
| ③ | ชิมาดะ | เนื้อหา Delivery Note | ไม่เตรียมจนกว่าจะอนุมัติ |
| ⑤ | บัญชี | ยอดโอนใน Zort = DN ที่เซ็นแล้ว | ทำให้ตรงกัน |
| ⑦ | หัวหน้า PC | เช้าวันแรก: ของโชว์ + สำรอง = จำนวนที่ส่ง | แจ้ง ผู้ประสานงาน และบัญชีวันนั้น แก้ Zort หลังชิมาดะอนุมัติ |
| ⑧ | หัวหน้า PC | ของเติมที่ได้รับจริง | กรอกใน Return Note |
| ⑨ | ผู้ประสานงาน + คลัง | วันปิดงาน: จำนวนกล่องและซีล | ไม่นับสินค้าที่หน้างาน |
| ⑩ | คลัง | วันทำการถัดไป: ซีลและของทุกกล่อง | ซีลขาดให้บันทึก |
| ⑪ | บัญชี | รับ + เติม − ขาย = นับได้ | ทำตารางส่วนต่าง |
| ⑫ | ผู้ประสานงาน → ชิมาดะ | ต่างแม้ 1 ชิ้น: หาสาเหตุ | โอนใน Zort หลังอนุมัติ |

:::warn
คนนับกับคนบันทึกใน Zort ต้องเป็นคนละคน การโอนใน Zort และรายงานยอดขายทำโดยฝ่ายบัญชีเท่านั้น
:::

เอกสาร: Delivery Note (ผู้ประสานงาน) · Return Note (ผู้ประสานงาน + คลัง) ยังไม่สรุป: วิธีส่งมอบเงินสด (⑨)
